# Releasing and repository settings

This page covers the repository settings, how a release is cut and published, and how a bad release is withdrawn.

- **What a release must meet:** [RELEASE_STANDARD.md](RELEASE_STANDARD.md).
- **The evidence recorded so far:** [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md).
- **Authorisation:** publishing a release needs its own approval, separate from merging changes.

## Protecting main

These settings cannot be applied from a script that only has push access, so set them once in the GitHub UI.

1. Open https://github.com/thatskiff33/unminute/settings/rules and click New ruleset, then New branch ruleset.
2. Name it `Protect main`. Set Enforcement status to Active.
3. Under Target branches, click Add target and choose Include default branch.
4. Tick these rules:
   - Restrict deletions
   - Block force pushes
   - Require linear history
   - Require a pull request before merging. Leave Required approvals at 0 (a solo maintainer cannot approve their own pull request), tick Dismiss stale pull request approvals when new commits are pushed, and tick Require conversation resolution before merging.
   - Require status checks to pass. Add every job from `.github/workflows/ci.yml`, `.github/workflows/changelog.yml`, `.github/workflows/audit.yml` and `.github/workflows/codeql.yml`: `Syntax check`, `Unit tests (Windows)`, `Requirements resolve (wheels only)`, `Ruff`, `PSScriptAnalyzer`, `Workflow lint`, `UI idle (headless Edge)`, `JavaScript syntax`, `Changelog entry`, `Dependency audit (pip-audit)`, `Analyse Python`, `Analyse JavaScript` and `Analyse workflows`. A check only appears in the picker after its workflow has run once, so add it after a pull request where it has gone green.
5. Leave Bypass list empty. Admins are then held to the same rules, which is the point.
6. Click Create.

From then on, all changes reach `main` through a pull request, and nobody can force-push or delete the branch.

Newer checks start outside that list:
- **How they become required:** after 10 consecutive green runs, and adding a check to the ruleset needs the owner account. The UI idle, JavaScript syntax, changelog entry, dependency audit and CodeQL checks joined the list by owner decision on 21 Oct 2026 (#121).
  - A `quality.yml` job moves into `ci.yml` when it becomes required, as UI idle and JavaScript syntax did.
  - The changelog job stays in `changelog.yml`, because that workflow re-runs when labels change. The dependency audit stays in `audit.yml`, because it also runs daily. CodeQL stays in `codeql.yml`.
  - `tests/test_consistency.py` takes the required set from every job in those four workflows and checks it against the list above. The one exception is a job run in parts by a matrix: the Windows unit tests run in chunks on separate machines at once (#386), and `Unit tests (Windows)` is the job that needs them all and passes only when every chunk passed. The chunks themselves are not required checks, so changing their number never touches the ruleset.
- **Report only:** `.github/workflows/quality.yml` keeps `Coverage (report only)` (lines and branches, child processes included), `Dead code (report only)`, `Quality report (report only)` (file size and growth, the largest modules and ruff C901 complexity against `tools/quality_baseline.json`, #365) and `Type check (report only)` (mypy against `tools/mypy_baseline.txt`, #413). They never block a merge and are not required. The coverage job stops at 45 minutes, so a slow run frees its runner instead of holding it for well over an hour (#406; the job's comment gives the timings).
- **Pending: the Pester job.** `PowerShell tests, Pester (report only)` in `quality.yml` becomes required once it has passed on 5 consecutive pull requests (the owner's decision, 23 Oct 2026, #111; in place of the 10 green runs above). Then it moves into `ci.yml` under a name without "(report only)", joins the list above, and the owner account adds it to the ruleset. Until then it reports only.
- **Pending: the Review record check (#410).** `.github/workflows/review-record.yml` runs `Review record` on every pull request. It passes only when a comment or review by an account with write access records an independent review of the head commit, as `tools/dev_status.py --review-record` reads it (the same parsing as `--pr`). The record has `Commit reviewed: <full sha>` (or a `Range reviewed:` line from a reviewed commit, or a `Range-diff: ... identical` line after a rebase) and `Reviewer: <session or agent>`, each on its own line, and the pull request names its writer in a `Writer:` line in its description; the check fails when a reviewer named is also a writer named. Every agent posts as the same GitHub account, so these names are the agents' own statements: the check shows that a record names a reviewer other than the writer, not who ran the review. A push starts a new run, which fails until a record names the new head. A run for a comment reports on `main`'s latest commit, not the pull request's head, so `.github/workflows/review-record-rerun.yml` re-runs the pull request's own run when a collaborator comments, and posting the record turns the check green. It is not required yet (the owner's decision, 27 Oct 2026): it runs for about a week of pull requests, then the owner adds it to the ruleset, it joins the list above and `tests/test_consistency.py` moves it to the required workflows. The re-run workflow runs only from `main`, so it cannot be tried before it merges.
- **Superseded runs are cancelled (#395).** In every workflow a pull request starts, a new push to that pull request (or, for the changelog check, a label change) cancels its older run that is still queued or running. The required checks then report on the new head from its own run; the cancelled run's checks stay on the old head, where the "Unit tests (Windows)" job still runs and fails because its chunks were cancelled. That job keeps `always()`, because a skipped required check counts as passing, so the new run starts only once it has finished (a few seconds on an Ubuntu runner, plus any wait for one). Pushes to `main`, the scheduled runs, manual runs and releases each run in a group of their own and are never cancelled. `tests/test_consistency.py` holds each workflow to that.
- **The changelog check:** it looks for a new or changed fragment in `changelog.d/` whenever a pull request changes what is shipped. An edit to `CHANGELOG.md` does not count. Add the `no-changelog` label to a pull request whose change is not worth a release note.

Already enabled at repository level (Settings > Advanced Security): Dependabot alerts, Dependabot security updates, secret scanning and push protection. Routine version bumps in `.github/dependabot.yml` cover GitHub Actions only (monthly, grouped, a 7-day cooldown); Python dependencies are re-locked instead (see "Workflow supply-chain rules"). CodeQL analyses the Python code, the JavaScript and the workflows from `.github/workflows/codeql.yml`.

## Protecting releases

The Release workflow relies on these owner settings. They were read back on 17 Oct 2026:

- **Tag ruleset** "Protect release tags": active. It stops a `v*` tag being created, moved or deleted by anyone but its bypass list. This is the control that keeps a collaborator from releasing: with it, only the owner can start a release. Confirm that the bypass list is the owner alone. Tags are matched by pattern, and whether that ignores case is not documented, so add `refs/tags/V*` too: IT's script refuses such a tag, but the workflow's own trigger may not.
- **`release` environment:** the repository owner is the required reviewer, and only `v*` tags can deploy to it. The publish job waits here for approval. Administrators can bypass it (GitHub's default): turn that off if anyone other than the owner gains administrator access.
- **The owner's sign-in on machines where agents run.** An agent, or malware running as the user, could use a signed-in owner account to create release tags and approve the deployment. Recommended: sign the owner out of `gh` and Git Credential Manager on those machines, and tag and approve on GitHub's website with two-factor sign-in.
- **Releases before v0.5.0** are not immutable, and their tags' `release.yml` still has a manual "Run workflow" route (with write access only; it has no signing rights).
- **Immutable releases** (Settings > General > Releases): turned on by the owner on 16 Oct 2026. This could not be read back with a collaborator's access, so confirm it before the first signed release. Once on, a published release's files and tag cannot change.
- **No rehearsal: v0.5.0-preview.1 is the first real run** (owner decision, 19 Oct 2026, on #111). The hosted-runner build, the attestations, the draft and the publish job had not run before it, so a local release build and check of the merged commit comes first ("Cutting a release", step 2). A failure after tagging burns that version: fix it and release as `-preview.2`. That happened: the hosted build of v0.5.0-preview.1 failed its signature check (19 Oct 2026), so nothing was drafted or published, and v0.5.0-preview.2 replaces it after the fix (#235).
- **The repository stays at `thatskiff33/unminute`** (owner decision, 21 Oct 2026, on #111; moving it to an organisation is not for now, which replaces the plan of 19 Oct 2026). The attestations, the default `-Repository` in `tools/intune/Get-VerifiedRelease.ps1` and IT's verification all name this address. The repository's address is part of the identity the attestations name, so changing it would mean changing that default and the docs together (a test fails in CI until they agree), checking the rulesets and the `release` environment again, and verifying a release against the new identity.

## Workflow supply-chain rules

The workflows run with the repository's token, so they are held to these rules. On every pull request the `Workflow lint` job (zizmor) flags unpinned actions, `${{ }}` expressions inside `run:` blocks, a missing default `permissions` block and checkouts that keep credentials. Asking for more permissions than a job needs, and the tool pinning, are checked in review.

- No permissions by default (`permissions: {}`); each job asks only for what it needs.
- Every action is pinned to a full commit SHA, with its version in a comment. To update one, resolve the new tag to its commit (`gh api repos/<owner>/<action>/git/ref/tags/<tag>`, and follow an annotated tag to its commit) and update both.
- Values from the event (tag names, inputs) reach scripts through environment variables, never through `${{ }}` inside a `run:` block.
- Checkouts use `persist-credentials: false`.
- **A workflow started by a comment** (`issue_comment`; only `review-record-rerun.yml`) runs from `main` with a token that can write even for a pull request from a fork. It checks out nothing, runs no pull request code, never reads the comment's text, acts only on comments on pull requests by accounts with write access, and its token can only re-run workflow runs and read pull requests. No workflow uses `pull_request_target` or `workflow_run`. `tests/test_dev_workflow.py` holds the two Review record workflows to this.
- CI tools come from `requirements/ci.txt` (and coverage from `requirements/ci-coverage.txt`, vulture from `requirements/ci-vulture.txt`, mypy from `requirements/ci-mypy.txt`, uv from `requirements/ci-lock.txt`, pip-audit from `requirements/ci-audit.txt`), installed with `--require-hashes`. All are generated by `tools/lock.py` from their `.in` files. PSScriptAnalyzer is pinned to one version and the SHA-256 of its PowerShell Gallery package (in its job in `ci.yml`), and must carry a valid Microsoft signature. Pester, for the report-only installer tests, is pinned to 5.9.1 and the SHA-256 of its PowerShell Gallery package in `tools/run_pester.ps1`, which uses no other file (a copy that does not match is removed and downloaded again) (#111 B6a). Both packages are downloaded directly, with up to 3 attempts, and kept in the Actions cache under a key of their version and SHA-256 only (#427). A copy from the cache is hashed again before use and downloaded afresh if it does not match, and each job fails if no matching package can be obtained.
- **The app's dependencies are hash-locked (#111 B1).** `requirements.in` lists the direct ones. `tools/lock.py` (uv, at the version pinned in `requirements/ci-lock.in`) writes `requirements.txt` with every package and its SHA-256 hashes, for Windows x64 and CPython 3.14, and the CI tool locks the same way. It keeps the versions already locked unless asked, refuses to move a package to an older version, only chooses versions public for 7 days (the cut-off time, in UTC, is recorded in each lock), and always takes hashes afresh from PyPI. Never edit a lock by hand: CI's `tools/lock.py --check` resolves each input again to the locked versions, with fresh hashes, and fails if a hash or a line differs. It takes the locked versions as given while they still resolve, so on a pull request `tools/lock.py --compare` also lists every version change against the base branch, for review, and fails on a downgrade the `.in` file does not pin. The package build installs only the lock, with `--require-hashes --no-deps`.
- **Monthly re-lock** (in place of Dependabot's routine Python updates; by an agent or by hand, with no automatic reminder): `python tools/lock.py --outdated` lists newer versions past the cooldown. Change a direct dependency's pin in `requirements.in` (most are pinned with `==`), or move an indirect one with `python tools/lock.py --upgrade-package <name>`, then run the usual checks and open one pull request. The torch family (torch, torchaudio, torchcodec, pyannote.audio) moves only as a set, with an end-to-end run on a real recording. The re-lock also adopts each new 3.14.x patch release of the runtime: update `PYTHON_VERSION` and `EMBED_SHA256` in `tools/build_package.py`, checking the published SHA-256 and the signatures (#178). A wheel that moves and has entries in `packaging/licences/manifest.json` fails the package build until its bundled components are checked again and their texts collected for the new version with `tools/collect_licences.py` ([PACKAGING.md](PACKAGING.md), "Licence texts", #176). Dependabot still raises security alerts and updates GitHub Actions.
- **A security fix inside the cooldown:** `python tools/lock.py --allow-newer <name>` (after changing the pin in `requirements.in`, for a direct dependency) moves that package to its newest version and records a dated exception in the lock, which lapses once the cooldown covers that version. `--check` lists every active exception.
- **A rollback:** pin the older version with `==` in the `.in` file; a re-lock otherwise refuses to move any package to an older version.
- **A Dependabot security pull request** for a Python package edits `requirements.txt` only, so it fails the lock check: treat it as an alert and re-lock instead.
- **Vulnerability audit.** `tools/audit.py` runs pip-audit over every lock on every pull request and daily (`.github/workflows/audit.yml`). A finding that cannot be fixed yet may be ignored in `requirements/audit-ignore.json`, with the package, a reason and an `until` date at most 90 days ahead; an expired entry fails the audit. Because the audit is a required check, a new advisory or an expired ignore turns every pull request red until a pull request that fixes it (a re-lock, or a dated entry in `requirements/audit-ignore.json`) merges; that pull request passes, since the audit reads its own locks. If PyPI or the advisory database cannot be reached, re-run the failed job once they can.
  - **Current exception:** GHSA-xcq7-p3pf-p88h (CVE-2026-114603, `opentelemetry-api` 1.45.0 and earlier, medium), until 22 Nov 2026 (the owner's decision of 23 Oct 2026 on #111, an owner-approved E2 widening for 30 days). The flaw is quadratic CPU use when parsing an inbound W3C `tracestate` header; Unminute runs no web server and accepts no inbound connections, and opentelemetry arrives only through pyannote.audio, with telemetry switched off before import (N1), so the code is not reachable. The next monthly re-lock takes opentelemetry 1.45.1 (which also brings protobuf 7 and two new beta packages) with full checks, and removes the entry and this line. The entry is honoured to the end of 22 Nov (UTC on the runner) and fails the audit from 23 Nov; `tests/test_dependency_locks.py` checks that each entry names one advisory and stops being honoured the day after its date.
- A new version of an action or tool is adopted only after it has been public for at least 7 days, so a compromised or broken release has time to be found.

## Before cutting a release

CI proves the code parses, the unit tests pass and the pins resolve. It does not run the models or the packaged app.

1. Check the release against [RELEASE_STANDARD.md](RELEASE_STANDARD.md). Part B lists each gate, where it runs and whether it is automated yet.
2. The merged commit is built and checked locally with `--release` before it is tagged ("Cutting a release", step 2).
3. The package is tested from its draft release, before anything is public ("Cutting a release", step 3).
4. **Phase C (#111) ships as one release.** From C2b-2 (schema 2) until C7 set `PHASE_C_COMPLETE = True` in `workspace/keystore.py`, no release could be prepared from `main`: `tools/changelog.py` refuses while the constant is `False` ("Phase C (#111) is not complete: no release can be prepared from this commit."), and `tests/test_consistency.py` then fails a change to `VERSION` (`PHASE_C_FROZEN_VERSION`, 0.5.0-preview.3). The last release before Phase C is v0.5.0-preview.3, tagged on 2558c5e. By the owner's decision of 19 Oct 2026 there is no matching check in `release.yml`. C7, the last Phase C slice, set the constant (the owner's decision, 21 Oct 2026). **Setting it was not release approval:** it only let a release be prepared, and the first Phase C release, v0.5.0-preview.4, needed the owner's new, explicit decision, which was given and used for it (#121). Its evidence includes the Phase C criteria ([RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md), "Phase C release evidence").
5. **The accessibility check covers WCAG 2.2 AA where it can (#298).** The owner made this a gate for the next release (22 October 2026): no release is published until #298 has landed ([RELEASE_STANDARD.md](RELEASE_STANDARD.md), "Accessibility against WCAG 2.2 AA").
6. **The Python runtime's support date (#178).** Every release confirms when 3.14's Windows binary releases end (PEP 745 plans the last for 5 October 2027) and, from 1 April 2027, reopens #178 if the runtime has not moved. See "Dated reminders" in [RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md#dated-reminders-every-release).
7. **The release register (#121, #411).** `python tools/dev_status.py --register` prints what stands between `main` and the next release: every open issue and pull request whose description has a line `Release gate: <gate>` (and, if known, `Next step: <who or what>`), with each pull request's state and the open pull requests that close each issue. Set the gate on the item itself; there is no register kept by hand.

## Cutting a release

The Release workflow (`.github/workflows/release.yml`, #111 B3) builds, signs and publishes a release when a version tag is pushed. There is no manual "Run workflow" route: the tag is the single record of what was released. The workflow publishes only after the repository owner approves it. That approval gates the workflow, not GitHub itself: anyone with write access can still edit or publish a draft by hand. So the publish job checks the published files afterwards, and IT verifies every download with `tools/intune/Get-VerifiedRelease.ps1`.

1. **Changelog and version.** On a branch, run `python tools/changelog.py vX.Y.Z` (for a preview, `vX.Y.Z-preview.N`).
   - It moves the fragments in `changelog.d/` into a new `## vX.Y.Z (YYYY-MM-DD)` section at the top of `CHANGELOG.md`, sets `VERSION` to `X.Y.Z` (or `X.Y.Z-preview.N`), and deletes the fragments.
   - `--summary "One line"` adds a line under the heading. `--date` sets the date if it should not be today.
   - **The first release after the rename (#136)** is not an update in place from 0.4.3 or earlier, and its fragment's bullet lands mid-list. Give it a summary that says so first, for example `--summary "Not an update in place from 0.4.3 or earlier: finish with the earlier version and uninstall it first (see Updates in docs/PACKAGING.md)."`
   - Review both files, then merge them to `main`. `VERSION` is the one source of the version: the package build reads it, and the workflow refuses a tag that differs.
   - **Promoting a preview to a full release:** run `python tools/changelog.py vX.Y.Z` as usual. The full section brings in the notes of every `## vX.Y.Z-preview.N` section (oldest first, each group's notes kept together) and any fragments added since, so users on Latest see everything since the last full release, as long as the previews were numbered `vX.Y.Z-preview.N` (notes from an abandoned preview of another version are not brought in: add a fragment if they still apply). The preview sections stay as they were; leave them as the script wrote them, and put install notes in `--summary`. A preview's summary is not carried over; give the full release its own. `python tools/changelog.py --preview vX.Y.Z` shows the notes first.
   - **After a preview that was tagged but never published** (its Release run failed, so nothing was drafted), the next preview carries its notes, since they never reached users. The script gives a preview only the fragments, so first move the unpublished preview's section back into `changelog.d/`: its ungrouped bullets in one file and each group in its own file under its group line, named to sort before the other fragments (such as `0-vX.Y.Z-preview.N.md`, `0-vX.Y.Z-preview.N-01.md`), and delete the section. Check that `python tools/changelog.py --preview` then prints what `--preview vX.Y.Z` printed before. Run the script for the next preview with a `--summary` that says the earlier one was tagged but never published. Keeping the old section as well would repeat its notes when the full release brings in its previews. v0.5.0-preview.2 was prepared this way.
2. **Tag the merged commit and push the tag.** The owner does this: the tag ruleset lets only its bypass list create release tags, and publishing a release needs its own approval (AGENTS.md).
   - **Before tagging, the owner reviews what changed in the release machinery since the last release.** An attestation proves where and from which commit a package was built, not that the code is benign, and agents merge their own pull requests:

     ```
     git diff <last release tag>..<commit> -- .github/workflows tools/build_package.py tools/windows_powershell.py tools/evidence.py tools/audit.py tools/intune/Get-VerifiedRelease.ps1 packaging requirements.txt requirements
     ```

     The list holds every `tools/` script the Release workflow runs and every `tools/` module the build loads by path (`tools/windows_powershell.py` starts the Windows PowerShell that checks signatures). It also holds `tools/intune/Get-VerifiedRelease.ps1`, which no release job runs: IT's check with it is what catches a release changed by hand after publishing (T14 in `docs/SECURITY_MODEL.md`), so a change that weakened it would otherwise not show here. `tests/test_release_workflow.py` fails if one of these is missing, for the path spellings it reads (its comment names them and its limit). App code the build runs, such as `workspace/asr_engines.py` for the model manifest and the packaged self-test, is not in the list: it ships in the package and is reviewed as app code.

   - **Before tagging, build and check the merged commit locally** with the release path the Build job runs. Work in a scratch clone with no push remote, so the local tag cannot reach GitHub, and delete the clone afterwards. Use the pinned CPython (`PYTHON_VERSION` in `tools/build_package.py`), or a virtual environment made from it, as `python`. Fetch first, so your checkout holds the merged commit. `<commit on main>` is its full 40-character SHA, not a short one: `tools/evidence.py names` compares all 40 characters (after fetching, `git rev-parse <short SHA>` prints it). Allow about 15 minutes: the check of v0.5.0-preview.2 (19 Oct 2026) took that long, with 5 minutes for the build from a warm cache, about 3 for `--verify-precompiled` and about 1 for the self-test. A first run with an empty `--cache` folder downloads the embeddable Python and every pinned wheel and takes longer; keep `<scratch>\cache` between checks to reuse it.

     ```
     git -C <your checkout> fetch origin --prune
     git clone --no-hardlinks <your checkout> <scratch>\src
     cd <scratch>\src
     git remote remove origin
     git checkout --detach <commit on main>
     git tag -a vX.Y.Z -m "Local check only, never pushed" <commit on main>
     python -I tools/build_package.py --release --out <scratch>\dist --cache <scratch>\cache
     python -I tools/evidence.py names <scratch>\dist\Unminute-X.Y.Z.zip X.Y.Z <commit on main>
     python -I tools/build_package.py --verify-precompiled <scratch>\dist\Unminute-X.Y.Z.zip
     ```

     Then extract the zip to an empty folder and, from its `Unminute-X.Y.Z\app` folder, run `..\runtime\python.exe -I -B -X disable-remote-debug -m workspace --self-test`. Every step must pass, and the self-test's last line must be `PASS`. A failure here costs no version number: fix it on a branch and check again.

   ```
   git tag -a vX.Y.Z -m "Unminute vX.Y.Z" <commit on main>
   git push origin vX.Y.Z
   ```

   The workflow then runs four jobs:
   - **Check** (Linux): the tag is `vX.Y.Z` or `vX.Y.Z-preview.N`, points at a commit on `main` and matches `VERSION`; the notes come from the dated changelog section; every lock passes the vulnerability audit at that commit.
   - **Build** (a GitHub-hosted Windows runner, nothing cached): `python -I tools/build_package.py --release` with the pinned Python (`PYTHON_VERSION` in `tools/build_package.py`). It checks that the zip's `version.json` names the tag's version and commit, runs the packaged `--self-test`, and checks that every shipped `.pyc` is what its source compiles to (`--verify-precompiled`). Then it signs build provenance and an SBOM attestation for the zip (Sigstore, `actions/attest`).
   - **Draft** (Linux): a draft release, visible only to people with write access, holding the zip, its `.sha256`, the SBOM (`.cdx.json`) and the attestation bundle (`.attestations.jsonl`).
   - **Publish** (the protected `release` environment): waits for the owner's approval (step 4).

   If the check or the build fails, nothing is drafted. A version number is never reused, and the tag ruleset stops a release tag being moved or deleted: fix the cause and release the next version number (the next `-preview.N` for a preview, otherwise the next patch version).
3. **Test the draft and attach the evidence.**
   - **Download and verify it.** In a new, empty folder, run `gh release download vX.Y.Z --repo <owner>/unminute --pattern "Unminute-X.Y.Z.*"`. Then run `gh attestation verify Unminute-X.Y.Z.zip --repo <owner>/unminute --bundle Unminute-X.Y.Z.attestations.jsonl --cert-identity https://github.com/<owner>/unminute/.github/workflows/release.yml@refs/tags/vX.Y.Z --source-digest <the tag's commit> --deny-self-hosted-runners`. `<owner>/unminute` is the repository, as in `tools/intune/Get-VerifiedRelease.ps1`, which checks published releases only.
   - **Rebuild it (recommended).** From a clean checkout of the tag, `python -I tools/build_package.py --release` should give the same SHA-256 ("Building the package locally" below), with the same Python, pip and zlib versions as the draft's SBOM records. Until #180 pins pip in the Release workflow, install that pip version first.
   - **Install it** with `install.ps1 -Package <folder>\Unminute-X.Y.Z.zip`, with its `.sha256` beside it. Run `runtime\python.exe -I -B -m workspace --self-test` from the installed version's `app` folder. Expect PASS.
   - **Release evidence** (docs/RELEASE_STANDARD.md, section 8). Run the five checks against the installed package from a clean checkout of the tagged commit, with the installed version's own Python. Run `git checkout vX.Y.Z`, then `git clean -ndX -- tools tests docs` to see which ignored files (such as `__pycache__`) would go, and `git clean -fdX -- tools tests docs` to remove them. It deletes them for good, so move anything else first. Clean means no change, no extra or ignored file, and nothing hidden from `git status` under `tools`, `tests` or `docs`. Start every check with `-B` so it writes no bytecode there. `<v>` is the installed version folder (`%LOCALAPPDATA%\Programs\Unminute\versions\X.Y.Z`). Use a copy of the models, never the live workspace, and a non-sensitive recording, such as a public meeting. The window checks need an unlocked screen.
     - **What each report records** (`tools/evidence.py`): the zip given with `--zip`; the checkout's commit, and whether it was clean; and whether the version folder held exactly that zip's files before and after the run. Names are compared exactly, and nothing may be missing, changed or added, with no link or extra folder.
     - **What stops a check before it starts:** a `--zip` that is not a package, a version folder that already differs from it, or a checkout that is not clean. The UI, accessibility and performance checks also stop under any other Python, without the app's flags (`-I -B -X disable-remote-debug`), or with app code from outside `<v>`.
     - **Exit code:** with `--zip`, a check exits 1 unless its evidence passes.

     ```
     <v>\runtime\python.exe -I -B -X disable-remote-debug tools\perf_check.py evidence-perf.json --app <v>\app --zip <folder>\Unminute-X.Y.Z.zip --leak-minutes 30
     <v>\runtime\python.exe -B tools\packaged_check.py <v> <model cache> <recording.wav> evidence-packaged.json --zip <folder>\Unminute-X.Y.Z.zip
     <v>\runtime\python.exe -B tools\packaged_crash_check.py <v> <model cache> <recording.wav> evidence-crash.json --zip <folder>\Unminute-X.Y.Z.zip
     <v>\runtime\python.exe -I -B -X disable-remote-debug tools\workspace_ui_check.py evidence-ui.json --app <v>\app --zip <folder>\Unminute-X.Y.Z.zip
     <v>\runtime\python.exe -I -B -X disable-remote-debug tools\accessibility_check.py evidence-accessibility.json --app <v>\app --zip <folder>\Unminute-X.Y.Z.zip --colour-mode both

     ```

     - The performance check measures against `docs/perf-budgets.json`, on the machine preparing the release. There is no named reference machine (#121): the budgets apply to whichever Windows machine measures, and the report records its specification (`machine`: processor, cores, memory, Windows build, power plan, mains or battery, graphics and drivers, the primary display's refresh rate, WebView2), never its name or its user. `tools/evidence.py check` refuses a performance report without that specification in full, and the check stops before measuring if it cannot read it. Put the line `tools/evidence.py machine` prints into the draft's release notes (edit the draft on GitHub) before approving: publishing keeps the draft's notes. Leave the machine idle, on mains power and the Balanced power plan, with the window visible for about two and a quarter hours. Keep the session unlocked and the window in view: the check keeps the display on for its own run (without changing the power plan) and records whether it could, and each window it measures in a visible state counts only if the display stayed on, the session was unlocked and the page drew; otherwise the run stops with exit 2 (#292). Keeping the display on does not stop a screen saver or an inactivity lock set by Intune or other policy (a laptop whose policy locks after about 60 minutes without input locks part-way through a release run): an unattended release run must account for that, or the run stops with exit 2 when the session locks. `tools/evidence.py check` refuses a performance report whose runs do not show each visible window drawn. For every v0.5.0 preview the owner chose the Performance plan instead, because the firm's staff laptops run on it (19 Oct 2026, on #111): the plan is recorded in the report's machine block and the line in the release notes. It counts as evidence only as a full release run within budget: at least 3 runs, 60 s settle and 300 s windows (the defaults), with the leak check (`--leak-minutes 30`), not `--quick`. Its recording states record synthetic audio, not the room; where managed policy turns microphone recording off they are reported as "not measured (policy)" (see `tools/perf_check.py --help`).
     - **Phase C evidence (#111 C7).** The performance check first measures the sealed store once, with no window (a few minutes; `tools/perf_check.py --help`), and `tools/evidence.py check` refuses a performance report without it; those figures and `workspace_s` are compared with budgets set from the first Phase C release run, v0.5.0-preview.4's medians by `perf_check.propose()` (plus 20%, rounded up to 0.01, at least 0.05 above the median; #430). Add `--compare <a local copy of the previous release's evidence-perf.json>` to set the figures side by side; nothing is fetched, and figures from a machine with another processor, memory, power plan or power source are marked not comparable. `packaged_check` and `packaged_crash_check` redirect `TEMP`, `APPDATA` and `USERPROFILE` into their throwaway folder, check that their scanner finds what was planted in a control file before they trust a clean scan, and fail on a crash dump there or on any file left in those folders that `tools/residue.py` does not explain. They also list your LocalLow folder and the model cache before and after (names, sizes and times only, never opened) and fail on a new or changed file nothing explains; another program writing there during the run can cause that, so run them on an idle machine. They do not yet show the window's WebView2 profile free of content (#418). They never read your own crash dump folders unless you add `--report-system-dumps` (counts only). `packaged_check` records about 10 seconds of synthetic audio through the app's own recording question: answer nothing, the check does. Its idle window, opened as the app is, still writes its own content-free Event Log entries and runs after the last scan and comparison (the owner's decision, 26 Oct 2026; #418).
     - **A file a library leaves (the owner's decision, 26 Oct 2026, #335).** If a check fails only on a file that a library left in the redirected folders, LocalLow or the model cache, and the file is shown to be a cache with no content, the agent running the release evidence may add a `residue.EXPLAINED` entry for it in `tools/residue.py`, with why it holds no content, in a pull request. Each new entry needs an independent review of that pull request before the checks are run again, and must be named in the evidence report: the reports list every entry they relied on (`left_explained`, `outside_explained`, and `explained` under the crash report's `outside`), and the release notes name each entry added for this release. Anything else stays unexplained and fails the check. An entry never lets a report carry your Windows user name: a file named after you still fails the report (below).
     - The UI and accessibility checks open a window for about a minute each (the accessibility check longer, as `--colour-mode both` audits each view in light and then in dark), and `packaged_check` opens one at the end. Release evidence uses both colour modes (the owner's decision, 22 October 2026, #111): `tools/evidence.py check` refuses an accessibility report that does not show every view the check visits audited in light and in dark. It names views left out entirely (a run that stopped early) apart from views missing one mode; either way, run the check again. Do not copy anything during the crash check.
     - Each check prints `EVIDENCE <kind>: PASS`. `tools/evidence.py check` prints `EVIDENCE COMPLETE` only when there is one passing report of each kind that names that SHA-256 and commit. Each report must also come from a release build, be made by a clean checkout of that commit, and have run on the unchanged package. Anything else is a failed gate: fix it and run the check again. Never edit a report. A failing report may hold error text with local paths, so do not attach one. A failing `packaged_check` or `packaged_crash_check` report can also list other programs' file names from your LocalLow folder (`outside_new`, `outside_unexplained`): never publish or share a failing report as it is. Every report (packaged, crash, performance, UI and accessibility) also fails when anything in it, a file name or its evidence block included, would carry your Windows user name or your profile folder's name (also its short 8.3 form, such as `PATEXA~1`, and the name decomposed, escaped or URL-encoded): the report written then says `report would carry the Windows user name` and lists only where (`user_name_at`, as key paths), never the value, and its evidence fails (#419). A name made only of the letters a to f is not counted inside a long run of hex digits (a SHA-256 or a commit id). Find what put the name there; an `EXPLAINED` entry cannot fix it.
   - Run one real, non-sensitive recording through the installed package with speaker identification on, and check the transcript looks right.
   - If a previous version is installed, check that the update keeps the workspace.
   - Work through docs/RELEASE_CHECKLIST.md. For a full release, decide explicitly on each open item in "Before a business release": either verified, or listed as a known limitation in the notes. The notes come from the changelog at the tag, so put known limitations there before tagging (`--summary`), or edit the draft's notes before approving.
   - Attach only the five `evidence-*.json` reports: the publish job refuses a draft holding any other file.
4. **Approve.** When the five reports are attached and the notes state the measuring machine, the owner opens the workflow run on GitHub, chooses Review deployments and approves `release`. Approve only after the evidence is attached. The publish job then checks:
   - the draft holds exactly the zip, its `.sha256`, the SBOM, the attestation bundle and the five evidence reports, with nothing missing or added;
   - the zip and the SBOM are the ones the build job made;
   - both attestations verify against this repository's Release workflow, the tag and the tag's commit, on a GitHub-hosted runner;
   - the evidence is complete and names that zip and commit (`tools/evidence.py check --commit`).

   Then it publishes, and checks that the published release holds exactly the files it checked, by name and by the digest GitHub records for each. It warns if the release is not immutable. With immutable releases on, the files and the tag can no longer change. If a check fails before publishing, fix the cause (for example, attach a missing report) and re-run the failed job, which asks for approval again. If the check after publishing says the files differ, someone changed the draft's files: withdraw the release ("Withdrawing a bad release") and release the next version number, as in step 2. If it says it could not read them, compare by hand: `gh api repos/<owner>/unminute/releases/tags/vX.Y.Z --jq '.assets[] | "\(.name) \(.digest)"'` against the SHA-256 of the files the job checked, which are the draft's files you downloaded.
5. **Release type.** A `vX.Y.Z` tag publishes a full release, which becomes Latest, the default download. A `vX.Y.Z-preview.N` tag publishes a pre-release that does not.

## Building the package locally

The Release workflow builds every published package. The same command builds it locally, to check a release or for development:

- `python -I tools/build_package.py --release` on Windows with 64-bit CPython 3.14 (without `-I` it refuses to run). It refuses a working tree with any change, untracked file or file hidden from `git status`, an ignored file under `tools/` (such as `tools/__pycache__`: `git clean -ndX -- tools` lists them and `git clean -fdX -- tools` removes them for good), and a HEAD that is not the commit of tag `vX.Y.Z`. It packages that commit's files as git stores them, never the working folder, and takes the version from `VERSION` (a `--version` that differs is refused; see PACKAGING.md).
- The command prints the zip's SHA-256 and writes the `.sha256` file and the bill of materials (`Unminute-X.Y.Z.cdx.json`) to `dist/`. The zip's `version.json` says `"release": true`; a build without `--release` says `false` and is never published.
- The build is reproducible: building the same commit again with the same Python, pip and zlib versions (listed in the bill of materials) gives the same SHA-256.
- `python -I tools/build_package.py --verify-precompiled <zip>` checks any package zip, with this machine's CPython of the package's version (not the package's own runtime). Every `.pyc` the package ships outside its standard library must be what its `.py` beside it compiles to, and a `.pyc` without its source is refused. The standard library inside `python3XX.zip` is not checked here: the build checks the official runtime against its pinned SHA-256, and for a downloaded zip the attestation covers it.

## Withdrawing a bad release

**When to withdraw.** Withdraw a release that has a severity 1 issue (defined in [RELEASE_STANDARD.md](RELEASE_STANDARD.md), section 14). Anything less serious is fixed forward in the next patch.

1. **Stop new downloads.**
   - Make the previous good release the default download: `gh release edit vPREVIOUS --latest`.
   - Add a warning at the top of the bad release's notes, saying what is wrong and which version to use instead.
   - Do not delete the release or its tag. A version number is never reused, and deleting it loses the record of what was shipped.
   - Once immutable releases are turned on (#111), the files cannot change. Whether the notes can still be edited is to confirm at that point.
2. **Managed devices.** Per-user installs: step 3 applies. Machine installs (`install.ps1 -Machine`, #111 B6b): in Intune, assign the previous version as new content of the same app (or supersede without "Uninstall previous version"), or run `install.ps1 -Machine -Rollback`. Going back to an earlier storage format removes the bad version from the computer, and users whose workspace it already changed see "ask your IT team" until the fix ships (strict withdrawal, the owner's decision B5-8). The first version with `-Machine` cannot be withdrawn to a version without it: uninstall it with `uninstall.ps1 -Machine` instead.
3. **People who installed it.**
   - Ask them to roll back, as described in [PACKAGING.md](PACKAGING.md): from `%LOCALAPPDATA%\Programs\Unminute\versions\<version>` (the bad version), run `powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1 -Rollback`.
   - Rollback is refused if the bad version changed the storage format. In that case, fix forward instead.
   - The first release after the rename (#136) has no earlier version in its install folder to roll back to. To go back past it, uninstall it and install the earlier release again, which opens that release's own workspace.
4. **Fix forward.**
   - Release the next version number through the normal process (the next `-preview.N` for a preview, otherwise the next patch version).
   - Its changelog entry says what was wrong and who was affected, without meeting content.
5. **Record it.**
   - Open an issue with the timeline, the cause, why the gates did not catch it, and the gate added so it cannot happen again.
   - Include no meeting content.

## Why there is no PyPI package

v0.1.0 shipped as source only. From v0.2.0 the release is a Windows package: a zip with a private Python runtime, installed by its `install.cmd` (see [PACKAGING.md](PACKAGING.md)). There is still no PyPI package, because:

- **The audience** is non-technical staff on managed Windows laptops. They run an installer, and a `pip install` step would be a regression for them.
- **The dependencies.** `requirements.txt` is a full hash-locked set, including torch, CTranslate2 and pyannote.audio. It was chosen because specific combinations break on CPU-only Windows. A PyPI package would need loose version ranges or a hard pin on torch, and neither works well in someone else's environment.
- **The package does what a PyPI package cannot:** it carries its own runtime, checks the machine, keeps the previous version for rollback, and holds back storage-format updates until the workspace is empty.
