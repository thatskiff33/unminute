# Encryption at rest

How Unminute encrypts meeting content on disk, what that protects against and what it does not. This is the design the code follows; threat IDs (T6 and so on) are in [SECURITY_MODEL.md](SECURITY_MODEL.md).

**Status (#111 phase C).** C1 adds the building blocks: `workspace/dpapi.py`, `workspace/vault.py` and `workspace/audiocrypt.py`, with their tests. C2a routes every read and write of the database's content columns through one place, the store's codec (`docs/WORKSPACE_DESIGN.md`, "Content columns"). C2b-1 (no change on disk) lets state checks read plain columns without opening content, pages the transcript in SQL and searches the text in one pass without the word timings, so only what is shown or searched is opened, and puts every deletion of a meeting's rows in the store. **C2b-2 seals the database's content columns (schema 2, "Database" below)**: titles, notes, passages, word timings, edits and their history, speaker names, redactions, hold reasons, source and watched-folder paths and the intake salt. **C2c seals the handoff templates** (`templates.sealed`, "Templates file" below). Still to come: C3 the audio files and recorder chunks with crypto-erase at cleanup, and C4 adds the locked screen for when Windows cannot unlock the key. Until C3 ships, the decoded audio (`media\<id>\audio.f32`) is protected by BitLocker only. Phase C ships as one release: no release can be prepared until C4b sets `keystore.PHASE_C_COMPLETE` (`docs/RELEASING.md`).

## What it protects against

* **T6, offline access to the disk.** A laptop that is off or hibernated, a removed disk or a disk image holds only ciphertext. Opening it needs Windows to unlock the user's key, which normally means this user signed in on this computer (see the DPAPI limits below).
* **T7, deleted content left behind.** Each meeting's content is sealed under that meeting's own keys, and cleanup destroys them (C3). A leftover copy of the content (database free pages, the WAL, SSD remnants) cannot be read once every copy of that meeting's wrapped key is gone too. The live database removes it with the controls it already has: `secure_delete`, WAL truncation and compaction. On an SSD, old physical copies of the wrapped key can survive like any other data; BitLocker covers them while the laptop is off. Copies of the whole workspace taken before cleanup (a backup, a disk image) still hold the wrapped key, so this Windows user can open those meetings from them.
* **T8, other accounts and backup agents** reading the workspace files see ciphertext (the database's content columns and the templates file; the audio from C3). An administrator who can act as the user, or who holds the domain's DPAPI backup key, can unlock it (below).

## What it does not do

* **Code running as the signed-in user can read everything.** Windows unlocks the root key for any process running as the user (that is how the app itself unlocks it). Malware in the session, or a person using the unlocked session, reads content as the app does. Endpoint protection is the control (T9).
* **DPAPI is not tied to one computer in every set-up.** Microsoft documents that a user with a roaming profile can unlock the data from another computer on the network, and that on an Active Directory domain anyone holding the domain's DPAPI backup keys can unlock any domain user's data. Microsoft describes the user's keys as derived from their password, so a disk image plus that password may be enough. What applies to Unlimit's laptops (Entra ID joined, hybrid or domain joined, roaming profiles or not) is to confirm on a pilot laptop (validation tracker #189).
* **Keys live in memory while the app runs.** Python cannot reliably wipe memory, so keys can appear in a crash dump, the page file or the hibernation file. BitLocker covers the page and hibernation files; crash-dump settings are part of the IT deployment guide (#111 slice D1). `workspace/dpapi.py` wipes its copy of the key and Windows's output buffer, but Python's own copies remain until the memory is reused.
* **Some facts stay readable.** Timestamps, states, counts, durations and receipts stay in plain text, so the update gate and `--status` work without a key. The length of each sealed value shows the approximate length of its text.
* **A sealed value is bound to its place, not to its version** (decided in C2b-2, #111 C1 review F9, the design's default Q1). An older copy of the same value (for example from a backup of the workspace) opens where it was stored: anyone who can write the workspace files can put an old value back in its own row. Protection against that would need state the same person could not also roll back, and everything (values, plain columns, `crypto_meta`) is in one file; the plain columns that decide behaviour (`holds.released_at`, `sources.delete_original`, `watched_folders.delete_originals`, `meetings.reviewed_at`) are not authenticated either. What schema 2 does add: a value opens only in the row it was written to, row ids never repeat, and a value moved to another parent (an edit's history to another passage, a name to another speaker pass) does not open. Phase C protects against reading (T6 to T8), not against code that can write as the user (T9).
* **Content written before C2b-2 and C3** by earlier versions may remain in free disk space in plain text, protected by BitLocker only. The schema 1 to 2 migration compacts the database file, so the old plain folder paths and intake salt are not left in its free pages or log, but an SSD can keep old physical copies.
* **If Windows loses the user's protection keys, the content is lost.** This can happen when an administrator resets the password without the old one, or a profile is damaged. The app then shows the locked screen (C4) and never falls back to plain text. Whether an Entra ID password reset keeps these keys is to confirm (#189).

## Key hierarchy

| Key | What it is | Where it is kept | What it protects |
| --- | --- | --- | --- |
| Root key | 32 random bytes per workspace | Only protected by Windows for this user (DPAPI, user scope, no prompt, Unminute's own entropy) | Everything, through the keys below |
| Wrap key | Derived from the root key (HKDF-SHA256, label `wrap`) | Never stored | Meeting keys, and nothing else (sealed with the label `key`) |
| Workspace key | Derived (label `workspace`) | Never stored | Workspace-wide values such as watched-folder paths and the templates file |
| Fingerprint key | Derived (label `fingerprint`), then one key per purpose | Never stored | HMAC-SHA256 fingerprints that replace plain hashes (of a file's SHA-256 digest, so large files are still hashed as they stream) |
| Check value | Derived (label `check`) | Stored | Tells a wrong or damaged root key from a good one, so the app can say which happened |
| Meeting text key, meeting audio key | 32 random bytes each, per meeting | Only wrapped under the wrap key, bound to their purpose and the meeting's random reference | That meeting's text and audio. Destroying the wrapped key is the erase. The text key seals values; the audio key is only used to derive per-file keys |

Every random value comes from the operating system's secure generator (`secrets`). HKDF is used without a salt, which RFC 5869 allows for a key that is already uniformly random.

**Labels and contexts** (`vault.encode`) are encoded as `unminute/v1/`, the label (lower-case letters, digits and hyphens), a zero byte, then each part of the context as a type byte (`s` text as UTF-8, `i` a signed 64-bit big-endian integer, `b` bytes), a 4-byte big-endian length and the part itself. Two different labels or contexts therefore never give the same bytes. The same bytes are the HKDF info of a derived key and the associated data of a sealed value.

## Database (schema 2, C2b-2)

`workspace/store.py` and `workspace/keystore.py`; the columns and their row tuples are listed in `docs/WORKSPACE_DESIGN.md`, "Content columns".

* **`crypto_meta`** (one row): the root key protected by the protector (`dpapi` in the app), its format (1) and its check value. Written only in the transaction that creates the database, or in the schema 1 to 2 migration's. A new workspace is built at `workspace.db.new` in one transaction, after the root key is protected, and renamed into place, so a first start whose key cannot be protected leaves no `workspace.db`. A schema-2 database without this row is refused (`missing`): the app never makes a new root key over existing data.
* **`content_keys`**: each meeting's text and audio keys, wrapped, made with the meeting in one transaction. Audio cleanup destroys the audio key in the transaction that records it; every deletion of a meeting row destroys its keys first (`Store.delete_meeting_row`; the foreign key refuses a meeting row whose keys remain). The audio key is used from C3a.
* **`recording_keys`** (used from C3b): one wrapped key per microphone recording, made before the recording starts, destroyed with `secure_delete` and a checkpoint of the write-ahead log (`Store.erase_checkpoint`, which retries while a reader such as `--status` keeps it busy). In the database rather than a file beside the chunks, so destroying it is not a file deletion whose clusters survive.
* **`recording_sources`** (used from C3b): which recording a meeting came from, with its details sealed. Removed at audio cleanup and with the meeting.
* **Sealed columns** are renamed `<name>_sealed`, so a read or write that went around the store fails with "no such column", and a migration's copy by column name cannot carry a plain value into one. Meeting values are sealed under the meeting's text key with the context `("meeting", meeting id, table, sealed column, *row)`; workspace values (folder paths, the intake salt) under the workspace key with `("workspace", table, sealed column, *row)`. The row tuple holds the row's id and the parent ids that never change (a passage's version, an edit history entry's passage, a correction's speaker pass).
* **Row ids never repeat**: passages, edit history and speaker corrections use `AUTOINCREMENT`, and their ids are chosen before the insert (a value is sealed for its row first) above both the largest id in use and the largest ever given.
* **Fingerprints** (HMAC-SHA256 under the workspace's fingerprint key, `Keyring.fingerprint`) replace the plain SHA-256 values that would let anyone with a copy of a recording confirm it was imported: `sources.original_fp` and `intake_content.fp` and `intake_seen.content_fp` (purpose `original`), `reviewed_snapshots.text_fp` (`snapshot`), and `watched_folders.path_fp` (`folder`, of the folder's identity: its real path compared without regard to case, which makes the folder unique now that its sealed path has a random nonce). `sources.audio_id` is the decoded audio's SHA-256 until C3a, which replaces it with the encrypted file's random id; it is not a fingerprint, and no release ships it.
* **The intake salt** (the key of the intake path hashes) is sealed. If it cannot be read, or is missing while files are recorded under it, a new one is made in the same transaction as clearing every folder's record of its files: the next scan records what is there and imports nothing it already had, and each folder's note says recordings added since its last check may need importing by hand, until that folder's next successful import.

**Errors.** One set, shared with C3 and C4:

| Error | Reason | Cause |
| --- | --- | --- |
| `KeyUnavailable` | `windows` | Windows would not unlock the root key (another user or computer, keys lost after a password reset, a damaged profile, or no Windows Data Protection at all). `code` is the Windows error number. |
| | `key` | It unlocked to something that is not this workspace's key (the check value differs). |
| | `protector` | The workspace was made with another protector (a test workspace opened by the app, or the reverse). |
| | `missing` | Schema 2 with no `crypto_meta` row, or rows in a database with no version. |
| `DamagedContent` | | A sealed value or a meeting's wrapped key does not open. |
| `KeyMissing` (a `DamagedContent`) | | A meeting's key row is absent (destroyed at cleanup, or never made). |

`KeyUnavailable`'s message is fixed text with no path or value. `Store(..., on_unavailable="raise")` (the default, and what the app uses until C4a) closes and raises; `"lock"` keeps the store open read-only: plain reads such as `--status` counts work, every seal, open and transaction raises the same `KeyUnavailable`, the connection is set to `query_only`, nothing is migrated or marked interrupted. Creating or migrating a workspace always raises when the key cannot be protected, and so does a database with rows and no version (`missing`, found before the key is read) in either mode; whether C4a's locked screen should cover that case is carried to C4a. **Before C4**, a key Windows will not unlock stops the app at start with a message and an incident code ("If Unminute cannot unlock its workspace" in the user guide); the diagnostics record holds the reason and the Windows error number only. `--status` and `--gate` read plain columns and need no key.

**Damaged values.** A value that does not open is reported, never shown as something else. Display reads show `[Could not be read]` in its place (the row lists it under `damaged`), and the meeting can still be discarded or cleaned up, because deleting rows and keys needs no content. Everything that produces text for use outside the app, or new content from old, refuses and produces nothing (`Store.strict`): the handoff preview, copy and save; confirming the transcript review (the reviewed snapshot is never a placeholder); saving or undoing an edit; changing speaker names. Search skips a damaged passage. Cleanup keeps an original whose path cannot be read, and a watched folder whose path cannot be read is not scanned and is never a deletion root. Transcription that meets a key that does not open rolls the part back and stops without counting a failure. A note the app writes itself (an error, a restart note) is left out if it cannot be sealed, so saving a state never fails because of it. Each case writes one content-free diagnostics event, `damaged_value`, with the table, the column name and a count. A user can still select and copy the visible placeholder by hand: it is a marker, not hidden content.

**Threads** (C1 security review N4). The codec and the keyring are used only by the store, under its own lock. The lock records which thread holds it; `_seal` and `_unseal` raise `RuntimeError` when the calling thread does not hold it (a runtime rule, not an `assert`). Every accessor fetches its rows and opens them under one hold of the lock, so a cleanup cannot destroy a meeting's keys in between. The wrapped text keys are loaded in one statement at open and unwrapped on first use; after a commit that destroyed keys, the cache is cleared and loaded again, and a rollback clears it.

**Key protectors.** The app uses only `keystore.DpapiProtector`; the `Store` has no codec or plain mode to choose. Tests use `tests/keyprotect.py`'s `TestProtector`, which keeps the root key in effect in clear text, so three guards keep it from a real workspace: it refuses any path under the real workspace folder (`store.under_workspace_root`, which lets it through only when `LOCALAPPDATA` is not set, as on Linux CI, and still counts a folder `default_root()` refuses as redirected, synced, on a network drive or a broken link), the store refuses any protector not named `dpapi` there as well (a constant, `keystore.APP_PROTECTOR`, so replacing the default protector class cannot change it), and `tests/test_content_access.py` checks that nothing in `workspace/` or `tools/` names it, that nothing in `workspace/` passes a protector except the `Workspace` handing its own to the store, and that every `Store` and `Workspace` built in `tests/` has the test protector apart from a named few that test the real one. `tests/` is not in the package. `--self-test` checks that Windows Data Protection protects and unlocks a random key, so a package that cannot use it fails the release build's self-test.

## Templates file (C2c)

The handoff templates (configuration, but a template can name people or clients) are kept in `templates.sealed` beside the database: their JSON, sealed as one value under the workspace key with the context `("workspace", "file", "templates.sealed")`. A workspace cell's context is `("workspace", table, sealed column, *row)`: no table is named `file`, and every row tuple has at least one part (each table's row id), so a cell's context has at least four parts and a file's three. Contexts are encoded with each part's type and length, so a file never opens as a stored value or the other way round, and a file sealed under another name or by another workspace does not open.

* **Built at first use, never while locked.** The app builds its templates the first time a template is shown, saved, restored or used in a session (`Workspace.templates`), not at start. While the store is locked nothing is read, converted or logged, and the store's `KeyUnavailable` is raised (`Store.file_sealer` refuses too).
* **Converting `templates.json`.** A plain file left by an earlier version is read at that first use, written sealed with the same titles, prompts and version numbers, then deleted. If it does not decode or parse (damaged, including JSON nested too deeply to parse), that gives no saved templates, as earlier versions read it, and the conversion logs one `templates_unreadable` event. A file that cannot be read at that moment (in use, or access refused), or whose sealed copy cannot be written, is left exactly as it is, and the next session's first use tries again. A file larger than 8 MB (the read stops at 8 MB plus one byte; earlier versions read any size), or whose sealed copy would be, is left exactly as it is and never converts. While a plain file is kept, that session shows the built-in templates, logs `templates_unreadable` once, and refuses every template save and reset with fixed wording (restart Unminute and try again; for a file too large, ask IT), so no `templates.sealed` is written that would win over the kept file at the next start. If both files exist and the sealed one opens (a crash between writing the sealed copy and deleting the plain one), the sealed one wins and the plain one is deleted. If the sealed one does not open (damaged, another workspace's, too large), a readable plain file is converted over it; one that cannot be read is kept as above. The plain file is deleted only once a sealed file that opens holds its content, or when the sealed file opened. A limit: an older `templates.sealed` that opens beside a newer `templates.json` still wins, and the plain file is deleted. That needs a development build from between C2b-2 and C2c (schema 2, still writing `templates.json`) run after a later build in the same workspace; no release can do it, because schema 2 and C2c ship in one release and earlier releases refuse a schema-2 workspace. Deleting it is an ordinary file deletion: its old blocks can remain on the disk, protected by BitLocker only, as for other content written before Phase C.
* **Writing.** The sealed file is written to a temporary file, flushed to disk and swapped into place, so a power cut leaves the old file or the new one. Leftover temporary files (`templates.sealed.*.tmp`, and an earlier version's `templates.json.*.tmp`) are removed at the first use in a session. A save whose sealed file would be larger than the read limit is refused.
* **Damaged or unreadable.** A `templates.sealed` that does not open (changed, cut short, from another workspace), does not parse, or is larger than 8 MB (`handoff.MAX_TEMPLATES_BYTES`; the read stops at 8 MB plus one byte and nothing is opened) is damaged: the built-in templates are shown, one content-free diagnostics event, `templates_unreadable`, is written, and the file is left until the next save replaces it (or a readable `templates.json` beside it is converted over it). A `templates.sealed` that cannot be read at that moment (in use, or access refused) is not damaged: the built-in templates are shown, the event is written, every template save and reset is refused with fixed wording (restart Unminute and try again), nothing is written or deleted (a `templates.json` beside it included), and the next session's first use reads it again. There is no new message on the page beyond those refusals.
* **What it does not do.** As for the database: code running as the user can read the templates, and an older copy of the file put back in its place opens (it is bound to its name, not its version). The file follows the workspace's root key: a workspace whose database is made afresh (a new root key) cannot open an earlier `templates.sealed`, and starts with the built-in templates (logged as `templates_unreadable`).

## Sealed values

A sealed value (a "cell") is: format version (1 byte), a random 12-byte nonce, the AES-256-GCM ciphertext, and its 16-byte tag. The associated data is the version byte plus the encoded label `cell` and the value's context, for example table, column and row. A value copied to another row, column or meeting therefore fails to open, as does any changed byte. Errors from opening never carry the value or chain an exception that does.

Random 96-bit nonces are safe for at most 2^32 values per key (NIST SP 800-38D, section 8.3). A meeting key seals one meeting's values: even one value per word with ten edits each, a 12-hour meeting is about 2^20. The workspace and wrap keys seal a few values per folder, template or meeting.

Wrapped meeting keys use the same format under the wrap key with the label `key` and the context `(purpose, meeting reference)`. A text key cannot be unwrapped as an audio key or as another meeting's key, and a wrapped key never opens as a stored value.

## Audio files

Decoded audio and recorder chunks are long and read in pieces, so they have their own format (`workspace/audiocrypt.py`):

| Part | Size | Content |
| --- | --- | --- |
| Header | 64 bytes, little-endian | `UMA1`; format version (1 byte); sample format (1 byte: 1 float32, 2 int16); channels (2 bytes); sample rate (4); frames per block (4, always 16,384); the file's random id (32); 16 reserved zero bytes |
| Header tag | 16 bytes | AES-256-GCM over nothing, nonce `ff ff ff ff` then 8 zero bytes, the header as associated data |
| Blocks | 16,384 frames each, plus a 16-byte tag | AES-256-GCM. Nonce: 4 zero bytes then the block's index (8 bytes, big-endian). Associated data: the header, the index (8 bytes, big-endian) and 1 byte that is 1 for the last block. The last block holds fewer than 16,384 frames, possibly none |

* **Key.** Each file has its own key: HKDF-SHA256 of the meeting's audio key, with the label `audio` and the context `(file id, then the caller's context)`, for example the meeting and which file it is. A block moved from one file, chunk or meeting to another does not open. The file id is in the info rather than the salt, because it is read from the file (RFC 5869, section 3.4).
* **Nonces.** Unique because every file has its own key, and a writer only ever creates a new file: it never appends to or rewrites one. It takes each block's index before writing the block, and after a failed write it refuses to write more or to finish the file, so no nonce is ever used twice under one key.
* **Opening.** The header tag is checked first, so a wrong key or context, or a changed header, fails at once. Then the last block is checked. Reordering blocks, cutting the file or adding to it is detected.
* **Finished and interrupted files.** A finished file ends with a block marked last. A file without one was interrupted (the app stopped while writing it). It opens only when the caller allows that, and then only up to its last whole block. Anyone who can change the file can also cut it to look interrupted, so only recovery may allow it, and it should call `verify()`. A file cut inside its header or header tag (written together when the file is created) is refused as damaged even then: nothing was saved in it. C3 decides how the recorder's recovery uses this.
* **Writers.** A writer's methods take a lock. After a failed write, flush or close it refuses to write more, and every later `close()` raises, so a retry never reports a finished file.
* **Reads.** Any range can be read, into a buffer the caller provides (`readinto`, for example a numpy array) or as a new one; each block is checked when it is read, and `verify()` checks every block. The overhead is 16 bytes per 64 KB block of mono float32 audio (0.02%).

## Choices

* **AES-256-GCM and HKDF-SHA256** from pyca/cryptography, which uses OpenSSL; **HMAC-SHA256** from Python's standard library. No primitive is written here.
* **Random nonces for cells, counters for audio.** Cells are written from many places, so a random nonce needs no shared state; audio blocks are many and written in order under a per-file key.
* **Key wrapping with AES-GCM rather than AES key wrap,** so a wrapped key is bound to its purpose and meeting.
* **DPAPI in user scope,** never machine scope, which any account on the computer could unlock.
* **Per-meeting keys rather than one key for the whole database or folder** (for example Windows EFS or an encrypted SQLite build): only per-meeting keys allow one meeting to be erased while the others stay.
* **No wrap-key rotation at cleanup** (decided 18 Oct 2026, the recommended option while the user was away; recorded on #111 and the C1 pull request). Rotating the wrap key would not help against a whole-workspace backup, which holds the root key's protected copy too, and BitLocker already covers leftover disk blocks while the laptop is off. The limit is stated under T7 above instead.
* **Versioned formats.** Each format has a version and every label has `v1`, so a later algorithm can sit beside the current one.

## Tests

`tests/test_vault.py`, `tests/test_audiocrypt.py` and `tests/test_dpapi.py`. Known answers built from the raw primitives pin every stored format: sealed values, wrapped keys, fingerprints, the root key's DPAPI entropy and audio files. A change that would make stored data unreadable fails a test. For the database: `tests/test_schema2.py` (opening, refusals, lock mode, the protector guards, binding, ids, known answers for every column's context and each fingerprint purpose, the lock rule, damaged values, erase points), `tests/test_content_access.py` (every content column sealed, nothing readable on disk) and `tests/test_update.py` (the 1 to 2 migration from a real schema-1 database, `tests/schema_v1.py`). For the templates file: `tests/test_handoff.py` (`SealedTemplatesTests` and `WorkspaceTemplatesTests`: nothing readable on disk, the conversion, damaged and oversized files, leftovers, the file context's known answer, first use only and nothing while locked).

## Sources

* [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final): AES-GCM, and the 2^32 limit for random nonces under one key (section 8.3).
* [RFC 5869](https://www.rfc-editor.org/rfc/rfc5869): HKDF; it works with or without a random salt (section 3.1), the extract step matters little for a key that is already uniformly random (section 3.3), and a salt should not be one an attacker can choose (section 3.4).
* [Microsoft: CryptProtectData](https://learn.microsoft.com/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata): DPAPI's user and machine scope, the no-prompt flag, and unlocking from another computer with a roaming profile.
* [Microsoft: DPAPI backup keys on AD domain controllers](https://learn.microsoft.com/windows/win32/seccng/cng-dpapi-backup-keys-on-ad-domain-controllers): keys protected by the user's password, and the domain backup keys that can unlock any domain user's data.
* [pyca/cryptography: authenticated encryption](https://cryptography.io/en/latest/hazmat/primitives/aead/): the AES-GCM interface used.
