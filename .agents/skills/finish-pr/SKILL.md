# Finish a pull request

The rules are in `AGENTS.md` ("Checks", "Delivery", "Authority") and `.github/pull_request_template.md`. This is the order to apply them in, not a second copy.

1. Run the checks that "Checks" names for what changed. For a Python change, run the tests it touches with `python tools/run_tests.py --strict-skips --only <modules>` and `ruff check .`, plus the UI checks for a UI change; CI runs the full suite on every push. Heavy runs take the heavy-run lock for at most about 15 minutes at a time, as "Checks" describes.
2. Read the final diff with `git diff origin/main...HEAD`. Look for unrelated edits, private material (P1) and invisible characters. Check its size too: a PR over about 1,000 lines outside `tests/` is split, or says why it cannot be ("Several agents or sessions"; `python tools/dev_status.py` shows each draft's size and flags any open PR over it).
3. Push, then open or update the PR from the template, with a `changelog.d/` fragment or the `no-changelog` label. Under "Checks run", list only the checks you actually ran, and say plainly what was not verified (E1).
4. As soon as the head is pushed, while CI runs, get an independent review of that fixed commit. The reviewer must not have written or directed the change, and must work in a separate checkout detached at that exact commit. Give the reviewer the code and the rules, not your conclusions. Ask for a security review when anything is under "Stop and ask".
   - In Claude Code, use an Agent with isolation "worktree", or another session. In that checkout, `/code-review origin/main...HEAD` reviews the fixed commit; a PR number would review whatever the PR's head is by then. `/security-review` reviews the checked-out branch against origin's default branch.
   - In Codex, use `/review`.
5. Record the reviewer, the commit, the verdict and the findings on the PR, with a line `Commit reviewed: <full sha>`, or `Range reviewed: <base>..<sha>` for a later delta whose base is already recorded as reviewed. Step 6 looks for these. Fix or answer each finding. Any change after the review needs its own review. After a rebase, use `git range-diff` as "Authority" describes, and when every commit shows "=", record a line `Range-diff: <reviewed commit>..<new head> identical`.
6. Run `python tools/dev_status.py --pr <n>`. It lists what still blocks arming the PR: failing or missing required checks, no review line naming the head commit, auto-merge armed on an unreviewed head, and a merge state GitHub reports as blocked. Its notes cover the draft state, required checks still running, failing checks that are not required, and the command to arm once nothing stops it. Its last line names what it cannot see, such as the review's verdict and open owner decisions; check those yourself.
7. As soon as the review approves the head (or its rebase, with an identical range-diff recorded) and no owner decision is open, run `gh pr ready <n>` and arm auto-merge pinned to it: `gh pr merge <n> --auto --squash --match-head-commit <sha>`. Don't wait for CI to finish: GitHub merges when the required checks pass. It doesn't wait for the others, so don't arm while a check that isn't required fails without its reason on the PR (with the required checks green, arming merges at once), and disarm with `gh pr merge <n> --disable-auto` if one fails later. Disarm before any further push; after a push, confirm auto-merge is off until the new head is reviewed, then re-arm. Watch with `gh pr checks <n> --watch` rather than polling on a timer. When PRs share files, agree the merge order with their owners before arming. Never push a tag or publish a release.
8. After the merge (GitHub deletes the branch), remove the worktree. Comment on the issue with the checks run, and tick a slice only where its tracking issue says to. Close the issue only when every acceptance criterion is met, and say which PRs did it.
